Full approved15-engine/122-task design JSON is byte-preserved, including historical proposed/planned labels; registry retains exact original E08 task IDs/dependencies. Design approval is not implementation acceptance.

createPlanningState/revisePlan/assertPlanningState/inspectPlans maintain pure private serializable plan histories. Each plan has contiguous revisions/exact predecessor and expected current revision. Earlier values remain detached. No command cache, durable audit, database transaction or crash recovery is claimed. Limits256 revisions/2MiB UTF8 aggregate; <=64 questions, <=16 hypotheses and32 leads/question, <=64 claim refs/list; per-string bounds also apply. Host input/CPU/heap limits are required; cloning/validation is not a sandbox.

A plan includes explicit questions/materiality rationale, parent question IDs, hypotheses with contrary-testing routes, leads and stop conditions. Parents must precede children in the same edition, so cycles/unknown parents fail. These are bounded literal planning descriptions, not executable commands or semantic proof that the proposed test is useful. Stop conditions never cause automatic action, termination or closure. Material questions from the preceding edition cannot be omitted or demoted; explicit deferral/resolution/authorized removal workflows remain pending. Question text can be revised under the same ID and every prior edition remains available. Hypothesis/lead removal preserves their prior editions. An empty hypothesis set or missing contrary route denies. Competing explanations can be added explicitly; the library does not invent one or infer support.

Basis/hypothesis claim refs must identify exact current claims in the supplied Knowledge snapshot on every append. A plan records unassessed claim references, not evaluated answers; it cannot insert answer/verification/closure/legal/editorial status. Inspection validates captured history but does not revalidate current claim usability. Current authenticated Knowledge/Evidence snapshots, Identity/session/resource policy, consent/rights and downstream correction impact remain host/integration prerequisites. Context is trusted host input, not authentication or a transferable permit. Prior plan records do not authenticate their actor/time/request metadata. Possession of serialized data exposes its private content, so host storage/access controls are mandatory.

Optional intakeCaseRef is only a scope-checked exact `case` ref, fixed for the lifetime of the logical plan. It does NOT load/authenticate an intake case, establish its existence/current revision, or duplicate case lifecycle. Hosts must use the owning Secure Intake workflow/authorization; no case create/close or completion routes exist here. No network/provider/model/worker/send/publication/payment/export service is added. PAM stays at its accepted foundation.
